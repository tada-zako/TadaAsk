# TadaAsk Frontend TypeScript Code Style

## 1. 文档定位

本文档记录前端 TypeScript 代码的通用编程风格倾向，用于帮助协作时保持代码容易阅读、审查和调整。

它不是完整工程规范，也不是严格 lint 规则。MVP 阶段应优先让代码清楚、具体、便于重构，而不是提前追求“架构完整”。

## 2. 基本原则

- 优先写直观具体的代码，让 reviewer 能顺着调用链理解真实行为。
- 避免为了未来可能发生的变化提前加入 factory、manager、callback、配置层或过多 helper。
- 当文件变重、逻辑重复、边界自然清晰时，再拆模块或抽象函数。
- 尊重已有库和框架的设计方式，不用额外封装扭曲库本身的返回模型或使用方式。
- 未确定的业务边界不要 mock 成“已经确定的设计”；用 TODO 标明后续需要接入的位置。

## 3. 文件与模块拆分

- 初期先把相关逻辑放在同一处，便于阅读完整流程。
- 拆分文件应有明确理由，例如复用、文件过长、职责边界清楚，或不同产品面需要独立演进。
- `shared` 只放真正跨 `console` 和 `widget` 复用的基础能力，不作为默认放置所有代码的目录。
- 不为了“看起来整洁”把几行胶水逻辑拆到单独文件。

## 4. 函数与抽象

- 小函数适合承载独立算法、复用逻辑或明确的业务动作。
- 不要用小函数隐藏关键流程细节，例如请求、错误处理、协议解析、状态流转等 reviewer 需要直接看懂的逻辑。
- 对象式 API wrapper 可以用于组织同一资源下的少量请求，例如 `projectApi.list()`；不要过早把前端请求层做成完整 SDK。
- 如果抽象让调用方必须记住额外约定，优先保留更直接的实现。

## 5. 类型使用

- 优先使用后端 OpenAPI 生成类型和已有本地类型。
- 不为了少写几个字符过早发明类型 helper。
- 只有当重复明显、语义稳定时，再提取类型别名或工具类型。
- 类型应帮助理解数据边界，不应让简单代码变得难读。

## 6. 注释风格

- 注释主要使用中文，必要时保留英文技术术语。
- 注释应解释为什么这样做、当前边界是什么、后续需要注意什么。
- 协议处理、外部接口、非显然的兼容逻辑和 TODO 应有简短注释。
- 避免解释显而易见的语句，例如“给变量赋值”“调用函数”。

## 7. 审查友好

- 代码应尽量减少无意义跳转，让 reviewer 能在少量文件内理解改动。
- “高级”抽象如果没有减少真实复杂度，就不是收益。
- MVP 阶段允许实现朴素一点，只要行为清楚、边界可调整、后续容易重构。
