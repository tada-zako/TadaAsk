# TadaWidget 前端 AI / Vibe Coding 协作说明

## 1. 文档定位

本文档记录 MVP 阶段前端开发中 AI / vibe coding 的参与边界与最低验收要求。

本文件是简易说明，不是完整流程规范。更细粒度的责任划分、代码审查规则和验收标准会在项目推进过程中逐步补齐。

## 2. 学习与掌握重点

开发者希望重点掌握：

- 前端项目整体构建方式。
- Admin Console 与 Visitor Widget 的运行时划分。
- 前端架构设计与目录组织。
- API、状态、构建、样式边界等核心工程决策。
- 关键核心文档中的设计说明。

开发者不计划深入参与所有 UI 细节：

- 具体页面布局细节可以更多依赖 AI / vibe coding。
- 视觉微调、组件组合、空状态、loading/error 状态等可由 AI 快速生成。
- 开发者主要对关键 UI 方向和最终可用性做 review。

## 3. AI 可参与范围

MVP 阶段允许 AI 直接参与前端任意文件或模块开发，包括但不限于：

- 页面与组件实现。
- Admin Console 布局。
- Widget UI。
- 表单、表格、弹窗、侧边栏等 UI 组合。
- API client、状态管理、stream 处理等核心模块。
- 文档、注释和设计说明。

当前不设置严格禁止区。对于核心工程文件，AI 可以参与设计和修改，但需要在输出中说明设计意图、影响范围和需要人工关注的点。

## 4. 分支与合并策略

当前项目处于 MVP 阶段，且属于个人项目。

因此：

- vibe coding 生成的 UI 允许直接进入 main branch。
- 暂不要求为 UI 原型建立复杂分支树。
- 后续如果项目复杂度提升，再考虑引入更严格的分支和 review 规则。

## 5. 最低验收标准

AI / vibe coding 生成的代码进入主线前，应至少满足：

- 能通过基本冒烟测试。
- 不破坏现有主要页面或构建流程。
- TypeScript 代码遵循项目 TS 标准开发规范。
- 不引入明显无关依赖。
- 不把临时 mock、调试代码或实验性 UI 伪装成最终功能。

冒烟测试的具体形式后续再细化。MVP 阶段可以先理解为：

- 页面能正常打开。
- 主要按钮和表单不报错。
- 基础 API/stream 流程不出现明显运行时异常。
- Widget 能正常显示、打开、发送消息并接收回复。

## 6. 核心文档要求

对于关键工程决策，需要保留适当的设计说明。

优先需要文档化的内容：

- 前端产品范围和 UI 约束。
- 前端架构与目录组织。
- API client 与 POST SSE stream 处理。
- Widget public API。
- Widget CSS tokens 和样式自定义边界。
- Admin Console 信息架构。

设计说明应保持简洁，重点解释：

- 为什么这样划分。
- 哪些内容是稳定约束。
- 哪些内容是 MVP 阶段临时选择。
- 后续可能扩展的位置。

## 7. 后续待细化

以下内容暂不在本阶段强制规定：

- 更细粒度的 AI 可修改/不可修改文件列表。
- UI 生成 prompt 模板。
- 视觉验收标准。
- 组件级测试要求。
- Playwright 或截图检查规范。
- mock 数据组织规范。
- 核心模块 review checklist。

这些内容会随着前端实现推进逐步补齐。
